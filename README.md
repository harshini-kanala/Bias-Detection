# Bias Detection and Mitigation in News Retrieval

This repository contains a two-track research workflow for bias-aware news retrieval and answer generation.

The project is built around two Jupyter notebooks:

- `bias_detection (2).ipynb` — the main bias-detection and retrieval pipeline
- `bias_detection_LLM.ipynb` — a parallel LLM-based notebook that uses Gemini 3.5 Flash Lite alongside the main pipeline to generate or refine answers using the retrieved evidence

The `bias_detection_LLM` workflow is run in parallel to the main retrieval pipeline, and Gemini 3.5 Flash Lite is used explicitly as the language model for the final answer-generation step.

## Project Overview

This project explores how to detect bias in retrieved news evidence and reduce source bias when answering user questions with a retrieval-augmented generation (RAG) workflow.

The system works by:

- cleaning and preparing a news dataset,
- splitting long article text into retrieval chunks,
- embedding text using a sentence-transformer model,
- retrieving the most relevant evidence for a query,
- analyzing the distribution of source bias among the retrieved results,
- re-ranking the evidence to reduce dominance by any single ideological source,
- passing the balanced evidence into an LLM for final answer generation.

## Notebooks Included

### 1) `bias_detection (2).ipynb`
This notebook contains the core retrieval and bias-mitigation pipeline.

It performs:

- dataset loading and cleaning,
- duplicate removal and null handling,
- text chunking,
- embedding generation with `all-MiniLM-L6-v2`,
- FAISS indexing for semantic search,
- top-K retrieval for user queries,
- bias distribution analysis,
- weighted re-ranking and mitigation,
- evidence selection for a balanced prompt.

### 2) `bias_detection_LLM.ipynb`
This notebook runs in parallel to the main pipeline and uses Gemini 3.5 Flash Lite.

It focuses on:

- taking the retrieved evidence generated by the retrieval workflow,
- building a prompt from balanced evidence,
- sending the prompt to Gemini 3.5 Flash Lite,
- generating a final answer that is more grounded in the retrieved sources,
- helping evaluate how LLM-based reasoning responds to the same evidence set.

This notebook is specifically designed to complement the pipeline by adding an LLM layer while preserving the bias-aware evidence filtering logic.

## Dataset

The project uses `bias_clean.csv`, which contains cleaned news articles with metadata and article text.

Columns include:

- `url`
- `topic`
- `date`
- `title`
- `site`
- `bias`
- `page_text`

The dominant bias labels in the dataset include:

- `left`
- `leaning-left`
- `center`
- `leaning-right`
- `right`

The dataset contains article text and political-leaning labels used to evaluate how retrieved evidence may skew toward a particular political source.

## Main Pipeline Workflow

The main notebook follows this process:

1. Load and clean the dataset
   - drop missing `page_text` values
   - convert raw text to string format
   - remove duplicate entries

2. Chunk long documents into smaller segments
   - chunk size: 150 words
   - overlap: 30 words
   - ignore very short chunks

3. Generate embeddings
   - uses `sentence-transformers`
   - model: `all-MiniLM-L6-v2`
   - embeddings are normalized for semantic retrieval

4. Build a FAISS index
   - stores embeddings in a vector index
   - supports efficient top-K similarity search

5. Retrieve relevant evidence
   - user queries are transformed into embeddings
   - FAISS returns the closest matching chunks

6. Attach bias labels to retrieved chunks
   - each chunk inherits the bias category of its source article

7. Detect and analyze bias in retrieved evidence
   - raw bias distribution is computed
   - weighted contribution is calculated using retrieval scores

8. Mitigate source dominance
   - re-rank evidence so a single source category does not dominate the final context
   - select a balanced mixture of sources

9. Prepare a final context for LLM reasoning
   - evidence is organized into a structured prompt
   - answer generation is grounded in retrieved content

## LLM Workflow

The `bias_detection_LLM` notebook is parallel to the main pipeline and explicitly uses Gemini 3.5 Flash Lite.

The workflow is:

1. retrieve or prepare textual evidence from the pipeline,
2. construct a prompt from the selected evidence,
3. pass the prompt to Gemini 3.5 Flash Lite,
4. ask the model to answer using only the evidence while avoiding unsupported claims,
5. review whether the model response is balanced and grounded.

This helps compare the behavior of a bias-aware retrieval pipeline with a lightweight LLM-based answer generator.

## Bias Mitigation Logic

The pipeline applies a lightweight mitigation strategy:

- similarity scores are converted into weights,
- bias contribution is aggregated across retrieved documents,
- evidence is re-ranked based on both relevance and balance,
- a diverse set of evidence is selected before formulating the final answer.

This reduces the chance that the answer is dominated by one political source or worldview, even when that source produces highly similar text.

## Example Query

The notebook uses example queries such as:

`Are women underrepresented in AI?`

The system then:

- embeds the query,
- retrieves the closest chunks from the dataset,
- checks the retrieved bias distribution,
- re-ranks evidence to balance source categories,
- creates prompt context for either the retrieval pipeline or the Gemini-based LLM model.

## How to Use

1. Open `bias_detection (2).ipynb` in Jupyter or Google Colab.
2. Run the retrieval and bias-mitigation cells in order.
3. Ensure `bias_clean.csv` is in the same folder.
4. Open `bias_detection_LLM.ipynb` separately to run the parallel Gemini 3.5 Flash Lite workflow.
5. Change the query in either notebook to test new questions.
6. Compare the retrieval-based evidence selection with the Gemini-generated answer.
